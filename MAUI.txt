1. Core .NET MAUI

You should be comfortable explaining:

What is .NET MAUI and how it differs from Xamarin.Forms
=> .NET MAUI is the evolution of Xamarin.Forms, providing a single-project structure, improved performance, 
and support for more platforms.

.NET MAUI (Multi-platform App UI) is Microsoft's cross-platform UI framework for building native mobile and 
desktop applications using C# and .NET from a single shared codebase.

It supports platforms such as:

Android
iOS
macOS
Windows

.NET MAUI is the evolution of Xamarin.Forms and is built on modern .NET.

| Xamarin.Forms                                        | .NET MAUI                                 |
| ---------------------------------------------------- | ----------------------------------------- |
| Older Microsoft cross-platform UI framework          | Successor to Xamarin.Forms                |
| Separate projects were commonly used for Android/iOS | Uses **single-project architecture**      |
| Based on Xamarin/.NET Framework-era tooling          | Built on modern **.NET 6+**               |
| Renderers                                            | Uses **Handlers**                         |
| More platform-specific project configuration         | Simplified platform configuration         |
| Xamarin.Essentials was separate                      | Essentials APIs are integrated into MAUI  |
| Xamarin support ended in 2024                        | Actively developed as part of modern .NET |
| Package/project structure was more complex           | Simplified project structure              |


Single-project architecture
Key difference: Single Project

In Xamarin.Forms, you commonly had:

MyApp
├── MyApp
├── MyApp.Android
└── MyApp.iOS

With .NET MAUI, the goal is:

MyApp
├── Platforms
│   ├── Android
│   ├── iOS
│   ├── MacCatalyst
│   └── Windows
├── Resources
├── Views
├── ViewModels
└── MauiProgram.cs

So you can maintain most of the application in one project while still writing platform-specific code when necessary.

MauiProgram.cs
MauiProgram.cs is the entry point for configuring a .NET MAUI application's services, dependency injection, fonts, handlers, 
middleware-like components, and third-party libraries. It contains the CreateMauiApp() method, which creates and configures 
the MauiApp.

public static class MauiProgram
{
    public static MauiApp CreateMauiApp()
    {
        var builder = MauiApp.CreateBuilder();

        builder
            .UseMauiApp<App>()
            .ConfigureFonts(fonts =>
            {
                fonts.AddFont("OpenSans-Regular.ttf", "OpenSansRegular");
                fonts.AddFont("OpenSans-Bold.ttf", "OpenSansBold");
            });

        builder.Services.AddSingleton<MainPage>();
        builder.Services.AddTransient<LoginPage>();
        builder.Services.AddTransient<LoginViewModel>();

        return builder.Build();
    }
}
What happens here?

The flow is roughly:

Application starts
       ↓
MauiProgram.CreateMauiApp()
       ↓
Create MauiApp builder
       ↓
Configure MAUI
       ↓
Register fonts
       ↓
Register services / ViewModels
       ↓
Configure libraries / handlers
       ↓
builder.Build()
       ↓
App starts


1. Configure the MAUI application
builder.UseMauiApp<App>();
This tells MAUI that App is the application's main class.

2. Dependency Injection

This is one of the most important responsibilities.

builder.Services.AddSingleton<IAuthService, AuthService>();

builder.Services.AddTransient<LoginViewModel>();

builder.Services.AddTransient<LoginPage>();

Then MAUI can inject dependencies:

public LoginViewModel(IAuthService authService)
{
    _authService = authService;
}

You don't need to manually do:

var service = new AuthService();

The DI container creates and manages it.

3. Register fonts
.ConfigureFonts(fonts =>
{
    fonts.AddFont("OpenSans-Regular.ttf", "OpenSansRegular");
});

Then you can use the font throughout your application.

4. Configure third-party libraries

For example, libraries such as Firebase, Maps, CommunityToolkit, etc. may require initialization/configuration here.

Conceptually:

builder
    .UseMauiApp<App>()
    .UseSomeLibrary();


5. Configure handlers

You can customize how MAUI controls map to native Android/iOS controls.

For example:

builder.ConfigureMauiHandlers(handlers =>
{
    // Custom handler configuration
});

This becomes particularly useful when you need platform-specific customization.


Dependency Injection
Dependency Injection (DI) is a design pattern where a class receives the objects/services it depends on 
from the outside 
instead of creating them itself.

Without DI ❌
public class LoginViewModel
{
    private AuthService _authService;

    public LoginViewModel()
    {
        _authService = new AuthService();
    }
}

The problem is that LoginViewModel is tightly coupled to AuthService.

If tomorrow you want to replace it with:

MockAuthService
StagingAuthService
ProductionAuthService

you have to modify the ViewModel.

With DI ✅

First create an interface:

public interface IAuthService
{
    Task<bool> LoginAsync(string username, string password);
}

Implementation:

public class AuthService : IAuthService
{
    public async Task<bool> LoginAsync(
        string username,
        string password)
    {
        // API call
        return true;
    }
}

Register it in MauiProgram.cs:

builder.Services.AddSingleton<IAuthService, AuthService>();
Then inject it:

public class LoginViewModel
{
    private readonly IAuthService _authService;

    public LoginViewModel(IAuthService authService)
    {
        _authService = authService;
    }
}

Now the DI container creates AuthService and provides it to LoginViewModel.

Think of it like this
MauiProgram.cs
      │
      │ registers
      ↓
IAuthService → AuthService
      │
      │ injected into
      ↓
LoginViewModel


Dependency Injection lifetimes
A DI lifetime determines how long an object instance should live and when a new instance should be created.

The three common lifetimes are:
Singleton
builder.Services.AddSingleton<IAuthService, AuthService>();

Singleton = one instance for the lifetime of the application/service container.

If multiple classes request IAuthService:

LoginViewModel ─────┐
                    │
HomeViewModel ──────┼──→ Same AuthService instance
                    │
ProfileViewModel ───┘

Example
builder.Services.AddSingleton<IAuthService, AuthService>();
If:

var service1 = ...;
var service2 = ...;

both resolve to the same instance.

When to use Singleton in MAUI?

Good candidates:

API service
Authentication service
Configuration service
App settings service
Logging service
Database service, depending on implementation

For example:

builder.Services.AddSingleton<IApiService, ApiService>();
builder.Services.AddSingleton<IAuthService, AuthService>();
Interview answer

Singleton creates one instance and reuses that instance throughout the application's lifetime. 
I use it for stateless or application-wide services where sharing the same instance is appropriate.

Transient
builder.Services.AddTransient<LoginViewModel>();

Transient = a new instance every time the dependency is requested.

Example:

Page A → LoginViewModel #1

Page B → LoginViewModel #2

Page C → LoginViewModel #3

Each is a separate object.

In MAUI

Transient is commonly useful for:

builder.Services.AddTransient<LoginPage>();
builder.Services.AddTransient<LoginViewModel>();

builder.Services.AddTransient<ContractPage>();
builder.Services.AddTransient<ContractViewModel>();

Every time the DI container creates/resolves one of these, it creates a new instance.

Why ViewModels are often Transient

Suppose the user opens:

Contract #100

and later:

Contract #200

You generally don't want both pages sharing the same ViewModel state.

Transient gives you a fresh instance.

Interview answer

Transient creates a new instance every time the service is requested. I commonly use it for ViewModels 
and page-specific services where each page/navigation instance should have its own state.


Scoped
This is the one that causes the most confusion in MAUI.

In ASP.NET Core, a scope is commonly associated with an HTTP request:

HTTP Request
     ↓
  Scope
     ↓
Service instance
But MAUI is a client application, not a request-based server application.

So you need to understand that a scoped lifetime doesn't automatically mean:

"one instance per API request."

That's an important interview trap.
Conceptually

Within the same DI scope:

Scope A
 ├── Service → Instance #1
 ├── Service → Instance #1
 └── Service → Instance #1

A different scope gets another instance:

Scope B
 └── Service → Instance #2
 So:

Singleton
    ↓
One instance globally

Scoped
    ↓
One instance per scope

Transient
    ↓
New instance each time

| Lifetime      | Instance                               | Typical MAUI usage              |
| ------------- | -------------------------------------- | ------------------------------- |
| **Singleton** | One for application/container lifetime | API/Auth/config services        |
| **Transient** | New instance every resolution          | Pages/ViewModels                |
| **Scoped**    | One per DI scope                       | Specific scoped workflows/state |

Remember this
Singleton
"One for everyone"

Scoped
"One per scope"

Transient
"New every time"

Imagine your application has:

LoginPage
HomePage
ContractsPage
ProfilePage

You could configure:

builder.Services.AddSingleton<IApiService, ApiService>();
builder.Services.AddSingleton<IAuthService, AuthService>();

builder.Services.AddTransient<LoginPage>();
builder.Services.AddTransient<LoginViewModel>();

builder.Services.AddTransient<ContractsPage>();
builder.Services.AddTransient<ContractsViewModel>();

Then the architecture looks like:

                    DI Container
                         │
          ┌──────────────┴──────────────┐
          ↓                             ↓
    Singleton Services            Transient Objects
          │                             │
    ┌─────┴─────┐                ┌──────┴──────┐
    ↓           ↓                ↓             ↓
ApiService  AuthService     LoginViewModel  ContractsVM
    │           │
    └───────────┘
          │
          ↓
       REST API

"Why wouldn't you register everything as Singleton?"
 
"Because Singleton means the same instance is shared for the lifetime of the application. That's not appropriate for objects 
that contain page-specific or user-specific state. For example, a ViewModel registered as Singleton could retain stale state 
and unnecessarily keep objects alive. I would generally use Singleton for application-wide services and Transient for page/ViewModel 
instances."

"What's the difference between Singleton and Transient?"

Singleton creates one instance and reuses it, while Transient creates a new instance every time the dependency is resolved.

"What's Scoped?"

Scoped creates one instance within a particular DI scope and reuses it inside that scope. Unlike ASP.NET Core, 
MAUI doesn't have a natural HTTP-request scope, so Scoped needs to be used with an explicitly created scope or a 
framework/library that manages scopes

Handlers vs Renderers
Both are mechanisms that connect a cross-platform UI control to its native platform control.
For example, when you write:
<Button Text="Login" />
you are using a MAUI/Xamarin.Forms abstraction.
But Android and iOS need their own native controls.
Conceptually:
Your XAML
   ↓
MAUI Button
   ↓
Platform-specific implementation
   ↓
Android Button / iOS UIButton

The major difference is how that mapping is implemented.

2. Xamarin.Forms — Renderers

Xamarin.Forms primarily used Renderers.

For example:

Xamarin.Forms Button
        ↓
ButtonRenderer
        ↓
Android Button

And on iOS:

Xamarin.Forms Button
        ↓
ButtonRenderer
        ↓
UIButton

A Renderer was responsible for creating/configuring the native control.
Example concept

Suppose you wanted to customize a Xamarin.Forms button.

You might create something like:


public class MyButtonRenderer : ButtonRenderer
{
    protected override void OnElementChanged(ElementChangedEventArgs<Button> e)
    {
        base.OnElementChanged(e);
        if (Control != null)
        {
            // Customize the native control
            Control.SetBackgroundColor(Android.Graphics.Color.Red);
        }
    }
}
So the Renderer sits between:
Xamarin.Forms control
        ↓
Renderer
        ↓
Native control

3. .NET MAUI — Handlers

.NET MAUI replaced the Renderer architecture with Handlers.

The architecture is:

.NET MAUI Control
       ↓
    Handler
       ↓
Native Control

For example:

MAUI Button
    ↓
ButtonHandler
    ↓
Android Button

4. Why did MAUI move to Handlers?

The main reason is to make the abstraction lighter and more efficient.

Renderers were more tightly coupled to the lifecycle of the native control and often involved a larger inheritance hierarchy.

Handlers use a property/mapping-based architecture.

For example:
MAUI Button
   │
   ├── Text
   ├── TextColor
   ├── FontSize
   └── Background
        ↓
   ButtonHandler
        ↓
   Native Button
The Handler maps MAUI properties to native properties.

5. What is a Handler Mapping?

This is an important senior-level interview topic.

You can modify how a MAUI control maps its properties to the native control.

For example:

Microsoft.Maui.Handlers.EntryHandler.Mapper.AppendToMapping(
    "CustomEntry",
    (handler, view) =>
    {
#if ANDROID
        handler.PlatformView.SetPadding(10, 10, 10, 10);
#endif
    });

Conceptually:

Entry
 │
 │ Padding
 ↓
EntryHandler
 │
 │ Mapping
 ↓
Android EditText

You're telling MAUI:

"When this MAUI property/control is handled, apply this additional native-platform customization."

6. Renderer vs Handler
| Xamarin.Forms Renderer                      | .NET MAUI Handler          |
| ------------------------------------------- | -------------------------- |
| Used primarily by Xamarin.Forms             | Used by .NET MAUI          |
| Renderer-based architecture                 | Handler-based architecture |
| More inheritance-oriented                   | Mapping-oriented           |
| Tightly coupled to native control lifecycle | Lighter abstraction        |
| `OnElementChanged()` commonly used          | Property/method mappings   |
| Custom Renderer                             | Custom Handler / Mapper    |
| Xamarin.Forms architecture                  | Modern MAUI architecture   |

"What is the difference between Handlers and Renderers?"

"Xamarin.Forms used Renderers to map cross-platform controls to their native platform controls. 
.NET MAUI replaced Renderers with Handlers. Handlers provide a lighter, mapping-based architecture 
where MAUI control properties and behavior are mapped to native platform properties. This reduces 
the need for heavy renderer inheritance and makes platform-specific customization more flexible. 
In MAUI, we can customize controls using Handler mappings or create custom handlers when required."

"Give me a real example where you used a Handler."

"If I need to remove the underline from an Entry on Android or change a native control's padding, 
I can use EntryHandler.Mapper and apply the native Android customization without creating a completely 
separate custom control."

3. TemplatedView
TemplatedView is used when you want a control whose visual appearance is defined by a template.
The important concept is:
Control
   ↓
ControlTemplate
   ↓
Visual UI
A TemplatedView provides the foundation for creating template-based custom controls.
For example:
public class MyCustomControl : TemplatedView
{
    public static readonly BindableProperty TitleProperty =
        BindableProperty.Create(
            nameof(Title),
            typeof(string),
            typeof(MyCustomControl));

    public string Title
    {
        get => (string)GetValue(TitleProperty);
        set => SetValue(TitleProperty, value);
    }
}

Then you can define a ControlTemplate:
<ControlTemplate x:Key="MyCustomControlTemplate">
    <Border Padding="10">
        <Label
            Text="{TemplateBinding Title}" />
    </Border>
</ControlTemplate>
And apply that template to the control.

This is useful when you want to create a custom control with customizable visual structure.

Think:

TemplatedView = custom control whose UI comes from a template

| Type            | Purpose                       | Example                    |
| --------------- | ----------------------------- | -------------------------- |
| `ContentPage`   | Complete screen               | LoginPage                  |
| `ContentView`   | Reusable UI component         | CustomerCardView           |
| `TemplatedView` | Template-based custom control | CustomButton/CustomControl |

Visual hierarchy
Application
   │
   ├── ContentPage
   │      │
   │      ├── ContentView
   │      │      └── UI elements
   │      │
   │      └── ContentView
   │
   └── Another ContentPage
While:
TemplatedView
      │
      └── ControlTemplate
              │
              └── UI structure

ContentPage represents a complete application screen and participates in navigation. ContentView is a reusable UI component 
that can be embedded inside pages or other views. TemplatedView is used to build custom, template-driven controls where the 
visual structure is provided through a ControlTemplate.

Resources and styles
1. What are Resources?
A Resource is an object/value that we define once and reuse throughout your UI.
For example, instead of writing this everywhere:
TextColor="#5A7890"
we can define it once:
<ContentPage.Resources>
    <Color x:Key="PrimaryColor">#5A7890</Color>
</ContentPage.Resources>
Then reuse it:
<Label
    Text="Welcome"
    TextColor="{StaticResource PrimaryColor}" />
Common resources
You can define:
Colors
Styles
Brushes
Fonts
Strings
Templates
Converters
Custom objects

2. What is ResourceDictionary?
Resources are stored in a ResourceDictionary.
For example:
<ContentPage.Resources>
    <ResourceDictionary>
        <Color x:Key="PrimaryColor">#5A7890</Color>
        <Color x:Key="ErrorColor">Red</Color>
        <x:Double x:Key="PagePadding">20</x:Double>
    </ResourceDictionary>
</ContentPage.Resources>
We can then use:
<VerticalStackLayout
    Padding="{StaticResource PagePadding}">
    <Label
        Text="Welcome"
        TextColor="{StaticResource PrimaryColor}" />
</VerticalStackLayout>

3. What are Styles?
A Style allows you to define common properties for a control once.
Without Style:
<Label
    Text="Name"
    FontSize="16"
    FontAttributes="Bold"
    TextColor="#5A7890" />

<Label
    Text="Email"
    FontSize="16"
    FontAttributes="Bold"
    TextColor="#5A7890" />
This is repetitive.
Instead:
<Style x:Key="TitleLabelStyle" TargetType="Label">
    <Setter Property="FontSize" Value="16" />
    <Setter Property="FontAttributes" Value="Bold" />
    <Setter Property="TextColor" Value="#5A7890" />
</Style>

<Label
    Text="Name"
    Style="{StaticResource TitleLabelStyle}" />

<Label
    Text="Email"
    Style="{StaticResource TitleLabelStyle}" />

Style = collection of property settings for a control.
4. Explicit vs Implicit Styles

Explicit Style
Has an x:Key.
<Style x:Key="PrimaryButtonStyle"
       TargetType="Button">
    <Setter Property="BackgroundColor"
            Value="#5A7890" />
    <Setter Property="TextColor"
            Value="White" />
</Style>
we must explicitly apply it:
<Button
    Text="Login"
    Style="{StaticResource PrimaryButtonStyle}" />

Implicit Style
No x:Key.
<Style TargetType="Button">
    <Setter Property="BackgroundColor"
            Value="#5A7890" />
    <Setter Property="TextColor"
            Value="White" />
</Style>

Now all Buttons within that resource scope automatically use the style.
<Button Text="Login" />
<Button Text="Register" />
<Button Text="Continue" />
All get the same styling.
Interview difference
Explicit style requires x:Key and manual application. Implicit style has no key and automatically applies 
to controls matching its TargetType.

5. Where can Resources be defined?
This is very important in real MAUI applications.
Page-level
<ContentPage.Resources>
    ...
</ContentPage.Resources>
Available within that page.
View-level
<ContentView.Resources>
    ...
</ContentView.Resources>
Available within that view.
Application-level
In App.xaml:
<Application.Resources>
    <ResourceDictionary>
        <Color x:Key="PrimaryColor">#5A7890</Color>
        <Style TargetType="Button">
            <Setter Property="TextColor" Value="White" />
        </Style>
    </ResourceDictionary>
</Application.Resources>
These can be shared throughout the application.

6. StaticResource vs DynamicResource
Another very common MAUI interview question.
StaticResource
<Label
    TextColor="{StaticResource PrimaryColor}" />

It looks up the resource when the UI is created.
Use it when the resource doesn't need to change dynamically.

DynamicResource
<Label
    TextColor="{DynamicResource PrimaryColor}" />

The control observes the resource and can update when the resource value changes.

Useful for things like:

Light/Dark theme
Runtime theme switching
Dynamic colors

For example:
<Color x:Key="PrimaryColor">
    ...
</Color>
If the resource dictionary changes the value, controls using DynamicResource can reflect the change.
StaticResource resolves a resource once, while DynamicResource maintains a relationship with the resource 
so the UI can respond when that resource changes.

such as colors, brushes, styles, converters, and templates. Styles encapsulate common control

global design tokens like colors and typography in shared resource dictionaries and use explicit 
or implicit styles to maintain consistent UI across the application.

StaticResource vs DynamicResource
In .NET MAUI, both StaticResource and DynamicResource are used to access values from a ResourceDictionary, 
but the key difference is what happens when the resource changes.

1. StaticResource
StaticResource resolves the resource when the XAML object is created.
<ContentPage.Resources>
    <Color x:Key="PrimaryColor">Blue</Color>
</ContentPage.Resources>

<Label
    Text="Hello"
    TextColor="{StaticResource PrimaryColor}" />
    he Label gets Blue.
If you later change the PrimaryColor resource, the Label doesn't automatically update.
Think:
StaticResource = resolve once

2. DynamicResource
DynamicResource creates a relationship between the control and the resource.
<ContentPage.Resources>
    <Color x:Key="PrimaryColor">Blue</Color>
</ContentPage.Resources>

<Label
    Text="Hello"
    TextColor="{DynamicResource PrimaryColor}" />

If the resource changes at runtime:
Resources["PrimaryColor"] = Colors.Red;
the Label can automatically update to Red.
Think:
DynamicResource = observe resource changes

|                  | `StaticResource`                  | `DynamicResource`      |
| ---------------- | --------------------------------- | ---------------------- |
| Resolution       | At creation                       | Dynamically            |
| Resource changes | ❌ UI doesn't automatically update| ✅ UI can update       |
| Performance      | Slightly cheaper                  | Slightly more overhead |
| Typical use      | Fixed styles/colors               | Theme/runtime changes  |
| Example          | Button style                      | Light/Dark theme       |

Real-world MAUI example

Suppose your app supports Light/Dark mode.
You might have:

<Color x:Key="PageBackground">White</Color>
<Color x:Key="TextColor">Black</Color>

Then:

<ContentPage
    BackgroundColor="{DynamicResource PageBackground}">
    <Label
        Text="Welcome"
        TextColor="{DynamicResource TextColor}" />

</ContentPage>
When the theme changes, you can replace/update the resources:
Light Theme
    PageBackground → White
    TextColor      → Black

        ↓ Theme Change

Dark Theme
    PageBackground → Black
    TextColor      → White
Controls using DynamicResource can respond to those resource changes.


I use StaticResource for resources that are effectively immutable during the lifetime of the UI, such as 
fixed styles, spacing, or constant colors. I use DynamicResource when the resource can change at 
runtime, most commonly for theme switching or other dynamic UI configuration. DynamicResource has 
some additional runtime overhead, so I wouldn't use it everywhere unnecessarily

x:DataType and compiled bindings
x:DataType tells MAUI what type the binding context is for a XAML element.
For example, suppose you have:
public class LoginViewModel
{
    public string Username { get; set; }
    public string Password { get; set; }
}
Normally:

<Entry Text="{Binding Username}" />
MAUI doesn't strongly know what Username is.

You can specify:

<ContentPage
    x:DataType="vm:LoginViewModel">

    <Entry Text="{Binding Username}" />
    <Entry Text="{Binding Password}" />

</ContentPage>
Now MAUI knows:

BindingContext

ObservableObject
ObservableObject is a base class from CommunityToolkit.Mvvm that makes a class support property-change 
notifications.

It is commonly used as the base class for a MAUI ViewModel.
using CommunityToolkit.Mvvm.ComponentModel;

public partial class LoginViewModel : ObservableObject
{
}
The main purpose is to implement:
INotifyPropertyChanged
so that when a ViewModel property changes, the UI can automatically update.

1. Why do we need it?

Suppose your XAML has:

<Label Text="{Binding Username}" />
And your ViewModel changes:
Username = "Vipin";
How does the Label know that Username changed?
Through INotifyPropertyChanged.
The flow is:
ViewModel property changes
        ↓
PropertyChanged event
        ↓
MAUI Binding system
        ↓
UI updates

2. Without ObservableObject

You have to write the notification code manually:
public class LoginViewModel : INotifyPropertyChanged
{
    private string _username;

    public string Username
    {
        get => _username;
        set
        {
            if (_username == value)
                return;

            _username = value;

            PropertyChanged?.Invoke(
                this,
                new PropertyChangedEventArgs(nameof(Username)));
        }
    }

    public event PropertyChangedEventHandler? PropertyChanged;
}
This works, but it's a lot of boilerplate.

3. With ObservableObject
public partial class LoginViewModel : ObservableObject
{
    private string _username;

    public string Username
    {
        get => _username;
        set => SetProperty(ref _username, value);
    }
}

SetProperty() handles:

Comparing old/new values
Updating the backing field
Raising PropertyChanged

So this:

set => SetProperty(ref _username, value);

is essentially handling the repetitive notification logic for you.

4. Even better: [ObservableProperty]

CommunityToolkit.Mvvm provides a source generator.
public partial class LoginViewModel : ObservableObject
{
    [ObservableProperty]
    private string username;
}

The toolkit generates the public property and notification code.

You can then use:
<Label Text="{Binding Username}" />
and:
Username = "Vipin";
The UI automatically receives the property-change notification.

Important:

The class must generally be declared as:

public partial class LoginViewModel : ObservableObject

because the toolkit's source generator generates additional code into the partial class.

WeakReferenceMessenger 

WeakReferenceMessenger is part of CommunityToolkit.Mvvm and is used for communication between different 
ViewModels, Views, and other objects without directly coupling them.
It implements the messenger/pub-sub pattern.

The key idea:

Sender
  ↓
Message
  ↓
Messenger
  ↓
Receiver

The sender doesn't need to know who receives the message.

1. Why do we need it?

Imagine you have:

Page A
  ↓
LoginViewModel

Page B
  ↓
HomeViewModel

After login, LoginViewModel wants to tell HomeViewModel:

"User has logged in. Refresh the data."

You could directly reference HomeViewModel, but that creates tight coupling.

Instead:

LoginViewModel
      ↓
"LoginCompletedMessage"
      ↓
WeakReferenceMessenger
      ↓
HomeViewModel

Now they don't know about each other.
2. Define a message

For example:

public sealed class LoginCompletedMessage
{
    public string UserId { get; }

    public LoginCompletedMessage(string userId)
    {
        UserId = userId;
    }
}

3. Send the message

From your Login ViewModel:

WeakReferenceMessenger.Default.Send(
    new LoginCompletedMessage("123"));

The messenger broadcasts the message to registered recipients.

4. Receive the message

Your Home ViewModel can register:

WeakReferenceMessenger.Default.Register<LoginCompletedMessage>(
    this,
    (recipient, message) =>
    {
        var userId = message.UserId;

        RefreshData();
    });

Now whenever:

WeakReferenceMessenger.Default.Send(
    new LoginCompletedMessage("123"));

is executed, the registered receiver gets it.

5. The flow
LoginViewModel
     │
     │ Send(LoginCompletedMessage)
     ▼
WeakReferenceMessenger
     │
     │ dispatch
     ▼
HomeViewModel
     │
     ▼
RefreshData()

The Login ViewModel doesn't need:

HomeViewModel homeViewModel;

This is the major benefit.

6. Why is it called WeakReferenceMessenger?

The important word is WeakReference.

The messenger uses weak references for recipients so that registering a recipient 
doesn't necessarily keep that object alive forever.

This helps reduce the risk of a messenger registration causing a memory leak when a 
ViewModel/View should otherwise be garbage-collected.

Conceptually:

Normal strong reference:

Messenger ──────────────> ViewModel
                           ↑
                     stays referenced


Weak reference:

Messenger - - - - - - - -> ViewModel
                           ↑
                     can be collected
                     when no strong refs remain

This is why WeakReferenceMessenger is generally preferable to building your own global static event system.

7. Real MAUI example

Imagine your app has:

RepairerListPage
RepairerDetailsPage

After saving a repairer:

RepairerDetailsViewModel
        ↓
RepairerUpdatedMessage
        ↓
WeakReferenceMessenger
        ↓
RepairerListViewModel
        ↓
RefreshRepairers()

Message:

public sealed class RepairerUpdatedMessage
{
    public int RepairerId { get; }

    public RepairerUpdatedMessage(int repairerId)
    {
        RepairerId = repairerId;
    }
}

Send:

WeakReferenceMessenger.Default.Send(
    new RepairerUpdatedMessage(repairer.Id));

Receive:

WeakReferenceMessenger.Default.Register<RepairerUpdatedMessage>(
    this,
    (recipient, message) =>
    {
        RefreshRepairer(message.RepairerId);
    });

This is useful when two parts of your application need to react to the same 
event but shouldn't directly depend on each other.

8. Strongly typed messages
You can also use Toolkit message types such as:
ValueChangedMessage<T>
For example:
WeakReferenceMessenger.Default.Send(
    new ValueChangedMessage<int>(123));
Receive:

WeakReferenceMessenger.Default.Register<ValueChangedMessage<int>>(
    this,
    (recipient, message) =>
    {
        int id = message.Value;
    });
You can also define your own message classes when the message has more meaningful domain information.

For production code, I generally prefer a named message such as:

RepairerUpdatedMessage

rather than an unexplained:

ValueChangedMessage<int>

because the intent is clearer.

9. Unregistering

You can explicitly unregister:

WeakReferenceMessenger.Default.Unregister<LoginCompletedMessage>(this);

Or all messages for the recipient:

WeakReferenceMessenger.Default.UnregisterAll(this);

With weak references, you don't always need manual unregistering purely for memory management, 
but explicit lifecycle management can still be useful when you want a recipient to stop responding 
while it remains alive.

10. WeakReferenceMessenger vs direct service injection

This is important at senior level.

Don't use Messenger for everything.

Use DI/service when:
ViewModel
   ↓
IRepairerService
   ↓
API

The ViewModel needs to call the service.

Use Messenger when:
ViewModel A
     ↓
notification/event
     ↓
ViewModel B

The sender doesn't need to know the receiver.

So:

DI is primarily for dependencies; Messenger is primarily for loosely coupled notifications/messages.

11. Messenger vs events

Traditional event:

This creates a direct relationship:
Subscriber
    ↑
    │ event
    │
Publisher

Messenger:

    ↓
Messenger
    ↓
Subscriber

The publisher doesn't need to hold a direct reference to the subscriber.

    ↓

    ↓

"Why use MVVM in .NET MAUI?"

Answer:

"I use MVVM to separate the UI from application logic and state. The View is responsible for presentation, the ViewModel exposes

What happens when a property changes?
What happens step by step?

Suppose your ViewModel has:

public partial class LoginViewModel : ObservableObject
{
    [ObservableProperty]
    private string username;
}

And XAML:

<Entry Text="{Binding Username}" />
<Label Text="{Binding Username}" />

When you do:

Username = "Vipin";

the flow is:

Username changes
      ↓
ObservableObject detects the change
      ↓
PropertyChanged event is raised
      ↓
MAUI Binding system receives the event
      ↓
UI elements bound to Username are updated
Without ObservableObject

You would have to manually raise PropertyChanged:

public class LoginViewModel : INotifyPropertyChanged
{
    private string _username;

    public string Username
    {
        get => _username;
        set
        {
            if (_username == value)
                return;

            _username = value;

            PropertyChanged?.Invoke(
                this,
                new PropertyChangedEventArgs(nameof(Username)));
        }
    }

    public event PropertyChangedEventHandler? PropertyChanged;
}

This event is what tells MAUI:

"The value of Username has changed. Refresh anything bound to it."

Important interview point

ObservableCollection<T> is different.

Property changes → INotifyPropertyChanged
Collection changes (Add/Remove/Replace) → INotifyCollectionChanged, provided by ObservableCollection<T>

For example:

Username = "Vipin";          // PropertyChanged
Repairers.Add(repairer);     // CollectionChanged
Senior interview answer

"When a ViewModel property changes, INotifyPropertyChanged raises the PropertyChanged event. MAUI's binding engine listens to that event 
and updates the UI elements bound to that property. CommunityToolkit.Mvvm's ObservableObject simplifies this by providing SetProperty and 
source-generated properties through [ObservableProperty]."

ObservableCollection vs List?
In .NET MAUI, the key difference is UI notification.

Feature	List<T>	ObservableCollection<T>
Stores items	✅	✅
Add/Remove items	✅	✅
Notifies UI when collection changes	❌	✅
Implements INotifyCollectionChanged	❌	✅
Good for CollectionView.ItemsSource with dynamic updates	❌	✅
Performance overhead	Lower	Slightly higher
Example with List<T>
public List<RepairerDetail> Repairers { get; set; }

If you do:

Repairers.Add(newRepairer);

the list changes, but MAUI doesn't automatically know that the collection changed.

So a CollectionView may not update.

ObservableCollection<T>
public ObservableCollection<RepairerDetail> Repairers { get; set; }
    = new();

Now:

Repairers.Add(newRepairer);

causes:

Add()
 ↓
CollectionChanged event
 ↓
MAUI Binding Engine
 ↓
CollectionView updates

Similarly:

Repairers.Remove(item);
Repairers.Clear();
Repairers.Insert(0, item);

notify the UI.

Important distinction

ObservableCollection only observes changes to the collection, not changes inside an item.

For example:

Repairers[0].Name = "New Name";

For the UI to detect that, RepairerDetail itself should implement:

INotifyPropertyChanged

So:

ObservableCollection
    ↓
Detects Add / Remove / Clear / Move / Replace

INotifyPropertyChanged on item
    ↓
Detects item property changes
Interview answer

"I use List<T> when the collection is mostly static or I don't need UI notifications. I use ObservableCollection<T> when a bound collection can 
change at runtime because it raises CollectionChanged events that MAUI's binding engine listens to. For item-level property changes, 
the item itself should implement INotifyPropertyChanged."

   ↓

   ↓

   ↓

If the JWT access token expires while the user is using the app, the API returns 401. I intercept that response in an authentication handler, 
use the refresh token to obtain a new access token, securely store the new tokens, and retry the original request. I also synchronize concurrent 
refresh operations so multiple API calls don't refresh the token simultaneously. If the refresh token is invalid or expired, I clear the 
authentication state and redirect the user to login. The user normally doesn't need to log in again unless the refresh process fails.

Task.Run() — when it is appropriate and when it isn't
Task.Run() is primarily useful for CPU-bound work that would otherwise block the UI or calling thread. For example, expensive calculations, 
image processing, or large data transformations can be moved to a ThreadPool thread using Task.Run(). I don't use it around naturally 
asynchronous I/O such as HttpClient, database async APIs, or file async APIs because those operations already release the calling thread 
while waiting. I also avoid using Task.Run() for UI updates because UI work belongs on the UI thread

CPU-bound  → Task.Run() may be appropriate
I/O-bound  → async/await directly
UI work    → UI thread

Task.Run() is not a synonym for async. It is a way to offload work to the ThreadPool; async/await is primarily about composing asynchronous 
operations without blocking while they wait.

    {
        IsBusy = false;
    }

28. Senior-level end-to-end flow

If interviewer asks:

"Explain how push notification works in your MAUI application."

A strong answer:

“The MAUI application initializes Firebase and obtains an FCM registration token. I send that token to our backend 
and associate it with the authenticated user's device. The backend stores the device registration and uses FCM to 
send push messages. On Android, FCM delivers directly through the Firebase messaging infrastructure, while on iOS 
FCM works with Apple's APNs for delivery. For foreground messages, the application handles the message callback and 
can generate a local notification or update the UI. For background notification messages, the platform can display 
the notification according to its rules. I also handle token refresh and update the backend when the registration 
token changes. For different environments, I maintain separate Firebase configurations to prevent staging and 
production tokens/projects from being mixed. On Android I configure notification channels and runtime notification 
permission, while on iOS I ensure APNs registration, capabilities, provisioning, and Firebase configuration are correct.”

 

Why would you get SENDER_ID_MISMATCH?
SENDER_ID_MISMATCH means the FCM token belongs to one Firebase project, but you're trying to send the notification 
using a different Firebase project/sender identity.
Simple example
Suppose your staging app is configured with:
Firebase Project: autoguard-staging
Sender ID: 111111111
The app generates:
FCM Token = ABC123
That token is associated with the staging Firebase project.

But your backend sends the notification using:

Firebase Project: autoguard-production
Sender ID: 222222222

Then FCM sees:

Token ABC123
      ↓
belongs to Sender ID 111111111

But request comes from
      ↓
Sender ID 222222222

❌ SENDER_ID_MISMATCH

Most common causes
Staging token + production Firebase credentials
Production token + staging Firebase credentials
Wrong google-services.json
Wrong GoogleService-Info.plist
Wrong Firebase project configured in the backend
Wrong Firebase service-account credentials
App was switched between Firebase projects without reinstalling/refreshing its token
Backend has an old FCM token stored for the device

In your MAUI application

You should verify this chain:

MAUI App
   ↓
google-services.json / GoogleService-Info.plist
   ↓
Firebase Project
   ↓
FCM Registration Token
   ↓
Backend database
   ↓
Firebase credentials used by backend
   ↓
FCM

The Firebase project that generated the token must match the Firebase project authorized to send to that token.

"SENDER_ID_MISMATCH occurs when an FCM registration token is associated with one Firebase project or sender ID, 
but the send request is authenticated against a different Firebase project. I would first verify the app's Firebase 
configuration, the token's environment, the backend service-account/project configuration, and whether an old token 
is stored in the database."


Why does OnMessageReceived() execute in one situation but not another?
The key point is: OnMessageReceived() is not guaranteed to run for every FCM message. Its behavior depends mainly on 
app state + payload type + platform.

Android
| App state  | Payload             | `OnMessageReceived()`           |
| ---------- | ------------------- | ------------------------------- |
| Foreground | Notification        | ✅ Usually yes                   |
| Foreground | Data                | ✅ Yes                           |
| Background | Notification        | ❌ Usually no                    |
| Background | Data                | ✅ Generally yes                 |
| Background | Notification + Data | ❌ Usually no; tap delivers data |

Why?

A notification payload tells Android:

"This is a user-visible notification. If my app is in the background, Android/FCM can display it for me."

So:

Backend
   ↓
FCM
   ↓
Notification payload
   ↓
App in BACKGROUND
   ↓
Android System displays notification
   ↓
OnMessageReceived() ❌

But when the app is foreground:

Backend
   ↓
FCM
   ↓
App is FOREGROUND
   ↓
OnMessageReceived() ✅
   ↓
You decide what to do

That's why developers often see:

"It works when the app is open, but OnMessageReceived() doesn't execute when the app is in background."

That's expected behavior for notification messages.
Data-only message

If you send:

{
  "data": {
    "type": "claim_updated",
    "claimId": "12345"
  }
}

Android gives your application the data through the messaging callback, including when the app is backgrounded, 
subject to Android/FCM delivery restrictions.
FCM
 ↓
Data message
 ↓
OnMessageReceived()
 ↓
Your code

Then you can create your own notification:

public override void OnMessageReceived(RemoteMessage message)
{
    var title = message.GetNotification()?.Title ?? "Notification";

    var claimId = message.Data.TryGetValue("claimId", out var id)
        ? id
        : null;

    ShowLocalNotification(title, claimId);
}

Notification + Data payload

For example:

{
  "notification": {
    "title": "Claim Updated",
    "body": "Your claim has been approved."
  },
  "data": {
    "claimId": "12345",
    "type": "claim_updated"
  }
}

When the app is backgrounded, Android can display the notification itself:
FCM
 ↓
Android
 ↓
Notification shown
Your OnMessageReceived() isn't normally where you handle that background notification.

When the user taps it, the data can be available through the launch/intent flow.
The important distinction

Don't memorize only:

Foreground = callback, Background = no callback.

That's too simplistic.

Instead remember:
                 FCM MESSAGE
                     │
          ┌──────────┴──────────┐
          │                     │
    Notification              Data
       payload               payload
          │                     │
          ▼                     ▼
   Platform may handle    App handles data
   notification           through callback
          │
    ┌─────┴─────┐
    │           │
Foreground   Background
    │           │
    ▼           ▼
Callback      System may
              display it

One more important issue: "background" ≠ "force-killed"

There is another common interview trap.

These are different:

Foreground
Background
Terminated / force-stopped
If the user force-stops an Android app, Android can prevent background delivery until the app is launched again.
So don't say:

"OnMessageReceived() always executes for data messages."

A better Senior-level statement is:

"OnMessageReceived() behavior depends on the message payload and application state. Notification messages can be handled 
by the OS when the Android app is backgrounded, whereas data messages are intended for application handling. I also 
consider Android background restrictions, Doze, force-stop behavior, notification permission, and message priority 
when troubleshooting delivery."
For your MAUI/FCM debugging

If you see:

App OPEN       → OnMessageReceived() ✅
App BACKGROUND → OnMessageReceived() ❌



Why can a notification arrive when the app is backgrounded but not trigger your foreground callback?
Because Android/FCM can handle a notification message at the OS level when your app is in the background, 
instead of delivering it to your OnMessageReceived() callback.
Example

If your backend sends:

{
  "notification": {
    "title": "Claim Updated",
    "body": "Your claim has been approved."
  }
}

When the app is foregrounded:
FCM
 ↓
Your FirebaseMessagingService
 ↓
OnMessageReceived()
 ↓
Your code

So you can handle it yourself.

But when the app is backgrounded:

FCM
 ↓
Android / FCM system
 ↓
Notification shown in system tray

OnMessageReceived() is not normally called for the notification portion.

Why does Android do this?

Because a notification payload is explicitly a user-visible notification. When your app isn't active, 
FCM can let the operating system display it without waking your application code.

This is why you can see:

🔔 Claim Updated

in the notification tray even though:
public override void OnMessageReceived(RemoteMessage message)
{
    // breakpoint doesn't hit
}

What if you want your callback to handle it?

Use a data message when appropriate:

{
  "data": {
    "title": "Claim Updated",
    "body": "Your claim has been approved.",
    "claimId": "12345"
  }
}

Then your application can process the data through the messaging callback, subject to Android's background-delivery 
restrictions.
“When the app is backgrounded, FCM can delegate notification messages to the Android system. The OS displays the 
notification directly, so the application's OnMessageReceived() callback doesn't necessarily execute. In the foreground, 
the app is active, so the message is delivered to the callback and the application decides how to handle it. If I need 
application-controlled processing, I generally use a data payload, while also accounting for Android background restrictions.”

 .NET Multi-platform App UI (.NET MAUI) is Microsoft's cross-platform framework that evolves Xamarin.Forms to let you build native desktop and mobile 
 applications for Android, iOS, macOS, and Windows from a single C# and XAML codebase.

 Key Components
 1: Unified Single Project Structure
 Unlike Xamarin.Forms (which required separate platform head projects) but .NET MAUI uses sinle .csproj file targeting multiple platforms via 
 SDK-style targeting (TargetFrameworks).
    => Platforms Folder: Houses platform-specific code (Andoid, iOS, MacCatalyst, Windows) when direct platform API or custom handleres are needed
    => Shared Assets:Fonts, images, splash screens, app icons, and raw assets are stored in one place and automatically converted into platform-native 
       formats during build.

 2: Handler Architecture
 .NET MAUI replaces Xamarin's heavy Renderers with lightweight Handlers.
    =>Decoupled Mapping: Uses interface-based mapping (e.g., IButton to Android.Widget.Button or UIKit.UIButton).
    =>Performance Gain: Removes the tight coupling of the old VisualElementRenderer, reducing object creation, layout passes, and assembly sizes.
    =>Easy Customization: Platform mappings can be modified globally or locally via PropertyMapper without needing to write custom subclassed 
    renderers.

 3: Application Lifecycle & Entry Point
    =>Apps start via MauiProgram.cs, which uses the standard .NET Generic Host pattern (MauiAppBuilder):
    public static class MauiProgram
    {
        public static MauiApp CreateMauiApp()
        {
            var builder = MauiApp.CreateBuilder();
            builder
                .UseMauiApp<App>()
                .ConfigureFonts(fonts => {
                    fonts.AddFont("OpenSans-Regular.ttf", "OpenSansRegular");
                });

            // Dependency Injection registration
            builder.Services.AddSingleton<IConnectivity>(Connectivity.Current);
            builder.Services.AddTransient<MainViewModel>();

            return builder.Build();
        }
    }

 4: Compilation & Execution Runtimes
    =>Android: C# compiles to IL, which executes alongside Java/Kotlin code via Mono VM (using Ahead-Of-Time/AOT or Just-In-Time/JIT compilation 
    depending on release settings).
    =>iOS / macOS (Mac Catalyst): C# is fully compiled via Ahead-Of-Time (AOT) compilation into native ARM binary code for direct execution on 
    iOS hardware.
    =>Windows (WinUI 3): Executes on top of .NET Core / CoreCLR runtime targeting Windows App SDK.


| Feature                           | Xamarin.Forms                                                                         | .NET MAUI                                                                 |
 
| **Project Structure**             | Multi-project head architecture (separate iOS, Android, and Core projects)            | **Single Project** (`.csproj` targeting multiple OSs)                     |
| **Control Mapping**               | **Renderers** (heavy, coupled to `VisualElement`, slow creation)                      | **Handlers** (lightweight, decoupled, faster rendering)                   |
| **Asset Management**              | Platform-specific folders (separate resolutions for each OS)                          | **Unified Resources** (images, fonts, splash screens auto-scaled at build)|
| **Framework Base**                | .NET Framework / Mono                                                                 | **Modern .NET** (.NET 6/7/8/9+)                                           |
| **Desktop Support**               | Basic UWP & experimental macOS                                                        | **First-class WinUI 3 & Mac Catalyst**                                    |
| **Web Integration**               | Limited web views                                                                     | **Blazor Hybrid** (`BlazorWebView` for Razor components)                  |
| **Configuration**                 | Scattered initialization (`AppDelegate`, `MainActivity`, `App.xaml.cs`)               | Centralized **`MauiProgram.cs`** via `.NET Generic Host`                  |
| **Dependency Injection**          | `DependencyService` (basic service locator)                                           | Built-in **Microsoft.Extensions.DependencyInjection**                     |

1. Single Project Architecture
In Xamarin.Forms, adding a custom font or image meant adding and configuring files across multiple project platforms. 
In .NET MAUI, resources are placed once in the Resources/ folder, and the compiler handles multi-resolution asset generation automatically.

├── Platforms/
│   ├── Android/
│   ├── iOS/

├── Resources/

│   ├── Images/

2. Handlers vs. Renderers
Xamarin Renderers: Tight coupling to VisualElementRenderer caused bloated view hierarchies, slow UI rendering times, and required 
writing custom renderers for simple modifications.

MAUI Handlers: Decoupled through interfaces (IButton, IEntry), improving performance up to 5x on startup and layout rendering. 
Controls can be customized globally or locally using lightweight property mappers:

// Customize all Entry controls across the app without custom renderers
Microsoft.Maui.Handlers.EntryHandler.Mapper.AppendToMapping("MyCustomEntry", (handler, view) =>
{
#if ANDROID
    handler.PlatformView.SetBackgroundColor(Android.Graphics.Color.Transparent);
#elif IOS
    handler.PlatformView.BorderStyle = UIKit.UITextBorderStyle.None;
#endif
});

In .NET MAUI, MauiProgram.cs is the central entry point for configuring and bootstrapping your application across all platforms. 
It utilizes the .NET Generic Host pattern (MauiAppBuilder), bringing standard .NET web and cloud architectural patterns into cross-platform 
desktop and mobile development.

Key Functions of MauiProgram.cs

App Initialization: Registers the root app class (App) and defines fonts, maps, or third-party SDK extensions.

Dependency Injection (DI): Registers services, ViewModels, and Views with built-in lifetime management (AddSingleton, AddTransient, AddScoped).

Control Customization: Configures cross-platform Control Handlers and property mappers globally.

Lifecycle & Logging: Sets up logging providers, debugging output, and platform-specific lifecycle events.

Code Example
using Microsoft.Extensions.Logging;
using Microsoft.Maui.Controls.Hosting;
using Microsoft.Maui.Hosting;
using MyMauiApp.Services;
using MyMauiApp.ViewModels;
using MyMauiApp.Views;

namespace MyMauiApp;

public static class MauiProgram
{
    public static MauiApp CreateMauiApp()
    {
        var builder = MauiApp.CreateBuilder();

        builder
            .UseMauiApp<App>()
            .ConfigureFonts(fonts =>
            {
                fonts.AddFont("OpenSans-Regular.ttf", "OpenSansRegular");
                fonts.AddFont("OpenSans-Semibold.ttf", "OpenSansSemibold");
            });

        // 1. Register Native & Business Services
        builder.Services.AddSingleton<IConnectivity>(Connectivity.Current);
        builder.Services.AddSingleton<IApiService, ApiService>();

        // 2. Register ViewModels
        builder.Services.AddSingleton<MainViewModel>();
        builder.Services.AddTransient<DetailViewModel>();

        // 3. Register Views / Pages
        builder.Services.AddSingleton<MainPage>();
        builder.Services.AddTransient<DetailPage>();

        // 4. Configure Handlers (Optional Customization)
        Microsoft.Maui.Handlers.EntryHandler.Mapper.AppendToMapping("NoUnderline", (handler, view) =>
        {
#if ANDROID
            handler.PlatformView.SetBackgroundColor(Android.Graphics.Color.Transparent);
#elif IOS || MACCATALYST
            handler.PlatformView.BorderStyle = UIKit.UITextBorderStyle.None;
#endif
        });

#if DEBUG
        builder.Logging.AddDebug();
#endif

        return builder.Build();
    }
}

Dependency Injection (DI) in .NET MAUI is powered by the built-in Microsoft.Extensions.DependencyInjection container. 
It allows you to register services, ViewModels, and Pages in MauiProgram.cs so that dependencies are automatically instantiated 
and injected where needed—promoting loose coupling, testability, and clean separation of concerns.

1. Service Lifetimes
When registering dependencies in MauiProgram.cs, choose from three primary lifetimes:
Lifetime        Method                                      Behavior in MAUI            
Transient       AddTransient<TService, TImplementation>()   A new instance is created every time it is requested. Best for detail pages, 
                                                            temporary ViewModels, or short-lived operations.
Singleton       AddSingleton<TService, TImplementation>()   A single shared instance is created the first time it is requested and persists for the 
                                                            lifetime of the application. Best for stateless services, caching, API clients, 
                                                            or main app pages/tabs.
Scoped          AddScoped<TService, TImplementation>()      In MAUI desktop/mobile apps (unlike ASP.NET Core web requests), Scoped behaves 
                                                            effectively like Singleton unless custom DI scopes are manually created.

.NET MAUI Shell is the foundation for application structure and navigation. It provides a single, unified system for managing 
container layouts (Flyout menus, Bottom Tabs, Top Tabs) and URI-based navigation across iOS, Android, macOS, and Windows.
Key Capabilities of Shell
Unified App Visual Hierarchy: Easily build flyout menus, bottom tab bars, and top tab bars using simple XAML declarations.

URI-Based Navigation: Navigate between pages using routes (e.g., //home/details?id=123) with full support for forward, backward, and absolute pathing.

Built-in Search & Customization: Direct support for integrated search bars (SearchHandler) and custom navigation bar components.

Optimized Performance: Pages are instantiated lazily on demand rather than all at launch, reducing app startup time and memory footprint.
